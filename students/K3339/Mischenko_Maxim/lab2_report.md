## Задача 1: Различия между threading, multiprocessing и async в Python

**Цель:** Написать три программы на Python, использующие threading, multiprocessing и async, для вычисления суммы чисел от 1 до N с параллельным разделением задачи.

### Описание реализации

Все программы используют общий подход:
- Задача разбивается на `K` подзадач (чанков).
- Каждая подзадача вычисляет сумму чисел в своём диапазоне с помощью функции `calculate_sum(start, end)`.
- Результаты подзадач суммируются для получения общего результата.
- Проверка корректности выполняется по формуле `N * (N + 1) // 2`.

Для демонстрации выбрано `N = 10 000 000` (10 миллионов), что позволяет увидеть разницу во времени выполнения без чрезмерного ожидания.

#### 1. Threading (`threading_sum.py`)

Использует модуль `threading`. Создаётся несколько потоков, каждый вычисляет свою часть суммы. Из-за Global Interpreter Lock (GIL) в Python потоки не выполняются истинно параллельно на CPU‑bound задачах, что приводит к ограничению производительности.

**Ключевые моменты:**
- Количество потоков: 4
- Функция `worker` сохраняет результат в общий список по индексу
- Основной поток ожидает завершения всех потоков с помощью `join()`

#### 2. Multiprocessing (`multiprocessing_sum.py`)

Использует модуль `multiprocessing`. Создаются отдельные процессы, каждый со своим интерпретатором Python, что позволяет обойти GIL и использовать несколько ядер CPU.

**Ключевые моменты:**
- Количество процессов: 4
- Используется `multiprocessing.Pool` и метод `map` для распределения задач
- Результаты собираются и суммируются в основном процессе

#### 3. Async (`async_sum.py`)

Использует модуль `asyncio` и ключевые слова `async`/`await`. Поскольку вычисление суммы – CPU‑bound операция, для её выполнения без блокировки event loop применяется `loop.run_in_executor`, который запускает функцию в отдельном потоке.

**Ключевые моменты:**
- Количество задач: 4
- Каждая задача выполняется в потоке через `run_in_executor`
- Задачи запускаются конкурентно с помощью `asyncio.gather`

#### 4. Sequential (`sequential_sum.py`)

Последовательная (однопоточная) реализация для сравнения производительности.

### Результаты измерений

Запуск на системе:
- ОС: Linux 6.6
- Python: 3.12.3
- Процессор: 4 ядра (предположительно)

Время выполнения (в секундах) для N = 10 000 000:

| Подход          | Время (с) | Ускорение относительно Sequential |
|-----------------|-----------|-----------------------------------|
| Sequential      | 0.2180    | 1.00x                             |
| Threading       | 0.2351    | 0.93x                             |
| Multiprocessing | 0.0754    | 2.89x                             |
| Async           | 0.2439    | 0.89x                             |

*Примечание: время измеряется как внутреннее время работы алгоритма, сообщаемое самой программой.*

### Анализ результатов

1. **Multiprocessing** показал наибольшее ускорение (~2.89×) благодаря использованию нескольких ядер CPU и отсутствию GIL.
2. **Threading** и **Async** оказались немного медленнее последовательной версии из‑за накладных расходов на переключение потоков и GIL (для threading) и на организацию event loop (для async).
3. **Async** с `run_in_executor` по сути использует те же потоки, что и threading, поэтому его производительность близка к threading.
4. **Sequential** версия служит базовой линией; её время примерно равно времени одного потока.

Выводы:
- Для CPU‑bound задач (тяжёлые вычисления) **multiprocessing** является предпочтительным подходом.
- **Threading** в Python подходит для I/O‑bound задач, где потоки могут ожидать ввода‑вывода, освобождая GIL.
- **Async** эффективен для большого количества I/O‑операций с низкими накладными расходами, но для чистых вычислений требует запуска в отдельных потоках/процессах.

## Задача 2: Параллельный парсинг веб-страниц с сохранением в базу данных

**Цель:** Написать три программы на Python, использующие threading, multiprocessing и async, для параллельного парсинга веб-страниц с сохранением данных в базу данных.

### Описание реализации

Все программы используют общий подход:
- Создаётся база данных SQLite с таблицей `web_pages` для хранения URL и заголовков страниц.
- Определяется функция `parse_and_save(url)`, которая загружает HTML-страницу, извлекает заголовок и сохраняет его в базу данных.
- Список из 15 популярных веб-сайтов разбивается на части для параллельной обработки.
- Измеряется время выполнения и сравнивается эффективность разных подходов.

#### 1. Threading (`threading_scraper.py`)

Использует модуль `threading` для создания нескольких потоков, каждый из которых обрабатывает свою часть URL-адресов. Поскольку веб-парсинг является I/O-bound операцией (ожидание сетевых запросов), потоки могут работать эффективно, освобождая GIL во время ожидания ответов от серверов.

**Ключевые моменты:**
- Количество потоков: 4
- Используются библиотеки `requests` и `BeautifulSoup`
- Результаты сохраняются в общую базу данных SQLite
- Применяется потокобезопасное соединение с базой данных (каждый поток открывает своё соединение)

#### 2. Multiprocessing (`multiprocessing_scraper.py`)

Использует модуль `multiprocessing` для создания отдельных процессов. Каждый процесс имеет собственный интерпретатор Python и независимую память, что позволяет полностью обойти GIL. Для I/O-bound задач multiprocessing также эффективен, но имеет более высокие накладные расходы на создание процессов и межпроцессное взаимодействие.

**Ключевые моменты:**
- Количество процессов: 4
- Используется `multiprocessing.Pool` для распределения задач
- Каждый процесс создаёт своё соединение с базой данных
- Результаты собираются через механизм межпроцессного взаимодействия

#### 3. Async (`async_scraper.py`)

Использует асинхронное программирование с `asyncio` и `aiohttp` для неблокирующих HTTP-запросов. Это наиболее эффективный подход для I/O-bound задач, так как позволяет обрабатывать множество соединений в одном потоке с минимальными накладными расходами.

**Ключевые моменты:**
- Используются `aiohttp` для асинхронных HTTP-запросов
- `aiosqlite` для асинхронной работы с базой данных
- `asyncio.gather` для конкурентного выполнения задач
- Ограничение на количество одновременных соединений: 10

#### 4. Sequential (`sequential_scraper.py`)

Последовательная (однопоточная) реализация для сравнения производительности. Обрабатывает URL-адреса один за другим, служит базовой линией для оценки ускорения от параллельных подходов.

### Результаты измерений

Запуск на системе:
- ОС: Linux 6.6
- Python: 3.12.3
- Процессор: 4 ядра
- Сеть: домашнее подключение (~100 Мбит/с)

Время выполнения (в секундах) для парсинга 15 веб-страниц (реальные измерения):

| Подход          | Время (с) | Ускорение относительно Sequential | Успешно обработано |
|-----------------|-----------|-----------------------------------|-------------------|
| Sequential      | 24.50     | 1.00x                             | 10 из 15          |
| Threading       | 11.09     | 2.21x                             | 11 из 15          |
| Multiprocessing | 11.10     | 2.21x                             | 11 из 15          |
| Async           | 13.79     | 1.78x                             | 12 из 15          |

*Примечание: не все сайты доступны для парсинга (некоторые возвращают ошибки 403, 503, таймауты), поэтому успешно обработано 10-12 из 15 URL. Различия в количестве успешных запросов обусловлены изменчивостью доступности сайтов и различиями в обработке ошибок между подходами.*

### Анализ результатов

1. **Threading** показал наилучшее ускорение (~2.21×) в данном тесте, что соответствует ожиданиям для I/O-bound задач. Потоки эффективно используют время ожидания сетевых запросов, освобождая GIL.

2. **Multiprocessing** показал практически идентичное время выполнения (~2.21× ускорения), что демонстрирует его эффективность для I/O-bound задач, несмотря на более высокие накладные расходы на создание процессов.

3. **Async** показал ускорение ~1.78×, что меньше, чем у threading и multiprocessing в данном конкретном тесте. Это может быть объяснено несколькими факторами:
   - Ограничениями на количество одновременных соединений (10)
   - Особенностями обработки ошибок в асинхронном коде
   - Сетевыми задержками и изменчивостью доступности сайтов между запусками
   - Тем не менее, async обработал больше сайтов успешно (12 из 15)

4. **Sequential** версия служит базовой линией и демонстрирует, насколько эффективны параллельные подходы для I/O-bound задач (все подходы дали ускорение от 1.78× до 2.21×).

Выводы:
- Для I/O-bound задач (веб-парсинг, работа с сетью, файлами) **threading** и **multiprocessing** показывают сравнимую производительность.
- **Async** в теории должен быть наиболее эффективным для большого количества I/O-операций, но на практике его производительность может зависеть от конкретной реализации, настроек и сетевых условий.
- **Multiprocessing** имеет более высокие накладные расходы на создание процессов, но для I/O-bound задач это не является критичным недостатком.
- Все параллельные подходы дают значительное ускорение (1.78-2.21×) по сравнению с последовательным выполнением для задач, связанных с ожиданием I/O.

### Заключение

Лабораторная работа наглядно демонстрирует различия между threading, multiprocessing и async в контексте как CPU-bound (вычисление суммы), так и I/O-bound (веб-парсинг) задач. Полученные результаты соответствуют теоретическим ожиданиям с некоторыми практическими нюансами:

1. **Для CPU-bound задач** (вычисление суммы чисел) наиболее эффективен **multiprocessing** (ускорение 2.89×), так как он позволяет использовать несколько ядер CPU и обходит ограничения GIL.

2. **Для I/O-bound задач** (веб-парсинг) в нашем тесте **threading** показал наилучшее ускорение (2.21×), что подтверждает его эффективность для задач с ожиданием I/O. **Multiprocessing** показал сравнимую производительность (2.21×), а **async** показал ускорение 1.78×.

3. **Threading** хорошо подходит для I/O-bound задач с умеренным количеством соединений, обеспечивая хороший баланс между простотой реализации и производительностью.

4. **Async** в теории должен быть наиболее эффективным для I/O-bound задач с большим количеством соединений, но на практике его производительность может зависеть от конкретной реализации, сетевых условий и настроек параллелизма.

5. Выбор подхода зависит от характера задачи и конкретных требований:
   - CPU-bound задачи → multiprocessing
   - I/O-bound задачи с умеренным параллелизмом → threading
   - I/O-bound задачи с очень большим количеством соединений → async
   - Простые задачи или прототипирование → sequential (как базовая линия)

Работа также демонстрирует важность эмпирического тестирования при выборе подхода к параллельной обработке, так как реальная производительность может отличаться от теоретических ожиданий из-за сетевых задержек, доступности ресурсов и особенностей реализации.
